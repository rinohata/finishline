# Phase 3 API実装・動作確認レポート

`docs/requirements.md` 6章・`docs/ui_spec.md` に基づくAPI実装。4エンドポイントすべてを実装し、
実際にサーバーを起動してリクエストを送り、動作を確認した（モックではなく実データ・実モデルでの応答）。

## 前提の実装

- 主定義は**定義A**（離脱=4のみ）。学習ラベル・プロファイル入力ともに保留(3)は使わない
- `data/dropout_curves.json` / `data/question_pool.json` は Phase 1 の定義Bのまま使用
- `api/services/profile.py`（Phase 1の純粋関数）をそのまま再利用
- `explain.py`（reasons/evidence生成）は `predict.py`（予測・スコアリング）と分離
- **起動時に `animelist.csv` を読まない**ことを確認済み（起動時間20.5秒、コード上も参照なし）。読むのは `anime.csv`・`question_pool.json`・`dropout_curves.json`・学習済みモデル・Phase 2で永続化したルックアップ（`data/processed/`）のみ
- 数値表示は完走率に統一。モデルは内部的に離脱確率を予測するが、レスポンスに変換前の値を含めることは一切ない

## 本番モデルの再学習

Phase 2 の検証で使ったN別モデルは実験用だったため、Phase 3では**N=3〜30を1つにプールし、
入力本数（`n_input`）自体を特徴量として追加した単一の本番モデル**を新たに学習した
（実ユーザーの回答数は可変であり、単一モデルで対応する必要があるため）。

- `models/dropout_predictor.lgb`（LightGBM, 定義A, 正例=離脱）
- テストAUC 0.8226 / PR-AUC 0.3024（ベースライン正例率5.56%）
- 特徴量列は `models/feature_columns.json` に保存、モデルカードは `models/model_card.json`

## 1. GET /questions

### 実装内容
- `q`（部分一致検索、ひらがな/カタカナ/全角半角正規化済み）、`genre`（複数選択）、`year_from`/`year_to`、`episodes_max`、`sort`、`limit`/`offset`
- `sort=split_score`（デフォルト・おすすめ順）は**split_scoreと人気度(登録者数)の複合スコア**に変更
- question_pool外（`anime.csv`全17,562作品）も検索対象。ヒットした場合は完走率を`population_completion_rate_B`から補う

### 複合スコアの係数調整
人気作は完走率がもともと高く（母集団平均94%前後）、エントロピー（split_score）が低く出るため、
単純な低ウェイトの合成では人気作が上位に出てこないことが実データで判明した。実際の
question_pool（250本）で重み `w` を掃引したところ:

| w | 先頭20本中、登録者数上位200位以内の件数 |
|---|---|
| 0.35 | 1件 |
| 0.50 | 2件 |
| 0.70 | 3件（要件を満たす最小値） |
| **0.75（採用）** | **4件** |
| 0.90 | 11件 |

安全マージンを見て **w=0.75** を採用し、実サーバーへのリクエストで先頭20本中4件が登録者数
上位200位以内であることを確認した（要件: 3件以上）。

## 2. POST /predict

実際にquestion_poolから8本抽出した回答（好き2・完走3・途中で止まった3）でリクエストし、200応答を確認。

- `profile`: type_name・耐久話数・完走率・completion_rate_avg・好む/避けるジャンル・curve（話数別のユーザー曲線 vs 全体平均曲線）をすべて実データから算出
- `at_risk`: **5件**、各件に `reasons` **3件**（episode_gap / genre / similarity / population のいずれかから実データ駆動で生成、テンプレート文言の穴埋めではなく実数値を使用）

## 3. POST /predict/single

### evidence
ユーザー自身の過去回答から、対象作品とジャンル一致度・話数の近さ・あらすじ埋め込み類似度を
組み合わせたスコアで**3件**抽出することを確認。`evidence_insight`も実データから生成
（ジャンル一致組の結果が揃っているか、話数近似組の結果が揃っているかを比較する簡易ヒューリスティック）。

### has_meaningful_peak / insufficient_data
Phase 1で「全話数5話以下の作品の85%で `peak_dropout_episode` が最終話になる」という
統計的不安定性が見つかっていた。この対策として、`predict.py`に
`has_meaningful_peak = (peak_dropout_episode < 総話数)` の判定を追加し、これが `false` の場合は
`insufficient_data: true` として返す（生JSON上は曲線データがあっても、信頼できないピークは
クライアントに渡さない）。以下の2パターンで実際に確認した:

| ケース | 元データ上のcurve | API応答 |
|---|---|---|
| 単話映画（peak=最終話=1話。統計的に不安定） | あり | `insufficient_data: true` |
| 元々`insufficient_data: true`の作品 | なし | `insufficient_data: true` |

### confidence / is_estimated
実際のラベル件数（`n_labeled_A`、訓練ユーザーのみから算出）に基づいて `high`(≥200) / `medium`(≥30) / `low`(それ未満)
を判定。カタログに存在しない・データが無い場合は `is_estimated: true` とし `confidence: low` に固定。

実際のカタログ内作品での確認: `confidence: high`（十分なデータがある作品）、`confidence: medium`
（データが少ない作品）の両方を実際のレスポンスで確認済み。

**なお、`anime.csv`は2020年時点のスナップショットのため、真の意味での「2021年以降の新作」は
本データセットに存在しない。** `is_estimated`のロジック自体は実装済みだが、実際に新作を投げて
確認することはできていない。Jikan API連携（要件定義書2.2、Phase 4以降・オプション）により
カタログ外の新作メタデータを取得する仕組みを別途実装する必要がある。

### already_answered
判定対象がすでに回答済みの場合、判定を行わず `{"already_answered": true, "anime_id": ..., "label": ...}` を返すことを確認。

## 5. UI仕様書の数値例の検証【最重要】

### 実測値

- **母集団完走率（定義A、全ユーザー）: 94.10%**（完走68,089,751件 / 離脱4,266,591件）。ユーザーが事前に想定していた「約94%」と一致
- 本番モデルのテストセット予測完走率の分布（N=3〜30混在、385,285件）:

| パーセンタイル | 予測完走率 |
|---|---|
| 最小 | 4.9% |
| 5% | 79.8% |
| 25% | 93.6% |
| 中央値 | 97.1% |
| 75% | 98.9% |
| 95% | 99.4% |

**「話題作だけど続かないかも」ブロック相当（ユーザーごとの予測完走率下位5件）に限定した分布:**

| パーセンタイル | 予測完走率 |
|---|---|
| 最小 | 4.9% |
| 10% | 66.8% |
| 25% | 80.3% |
| 中央値 | 90.9% |
| 75% | 95.0% |

### UI仕様書5.2の5段階しきい値を実測分布に当てはめた結果

| 判定文言のしきい値 | 全体予測に占める割合 | at_risk相当（下位5件）に占める割合 |
|---|---|---|
| 80%以上「✓ 問題なく見られそうです」 | **94.9%** | **75.5%** |
| 60-79%「✓ 完走できる可能性が高いです」 | 4.2% | 17.7% |
| 40-59%「〜 五分五分です」 | 0.6% | 4.6% |
| 20-39%「⚠ 完走は難しいかもしれません」 | 0.2% | 1.1% |
| 20%未満「⚠ 最後まで届きにくいかもしれません」 | 0.2% | 1.1% |

### 問題点

UI仕様書のモック例（「あなたの完走率26% / 一般平均74%」）は実測分布から大きく外れている
（実測での最小値は4.9%で技術的には範囲内だが、下位5件中央値90.9%と比べると極端な外れ値）。
より深刻なのは、**現行の5段階しきい値のままだと「話題作だけど続かないかも」ブロックに表示される
作品（本来「危険」であるはずの下位5件）の75.5%が「✓ 問題なく見られそうです」という
安心させる文言になってしまう**ことである。これは機能の意図（続きにくい作品を警告する）と
表示文言が矛盾する。

### 提案

1. **絶対値表示は維持する**（要件通り、完走率のまま。離脱確率は出さない）
2. **5段階しきい値を実測分布に合わせて再較正する。** 目安として、下位5件の分布（10%点66.8%、
   25%点80.3%、中央値90.9%、75%点95.0%）を参考に、たとえば次のような再配分を提案する
   （最終値はデザイン判断を要するため、あくまで実データに基づく叩き台）:
   - 95%以上 → 問題なく見られそうです
   - 85-94% → 完走できる可能性が高いです
   - 70-84% → 五分五分です
   - 50-69% → 完走は難しいかもしれません
   - 50%未満 → 最後まで届きにくいかもしれません
3. **一般平均との相対比較（`一般平均74%`のようなペア表示）を主役に据える。** 絶対値が
   85〜99%に密集していても、「あなたはXX% / 一般平均94%」という相対差は依然として意味のある
   シグナルであり、UI仕様書のモックが元々意図していた設計（4.3・4.5ブロックの対比表示）は
   有効。ただしモック内の「一般平均74%」という数値自体は非現実的なので、実際の
   `population_completion_rate`（本APIが返す実測値、多くは85〜98%程度）に置き換える必要がある
4. 上記いずれを採るにせよ、**モック文言の数値例（26%/74%など）は実装・デザインレビューの
   両方でそのまま転用しないよう注意喚起する**（実データとかけ離れているため、閾値設計やコピー
   のミスリードの原因になりうる）

## 追記: at_risk / percentile の再修正

### 修正1-b: at_risk から相対条件（平均-1σ）を削除

前回実装した相対条件は、実測（本番候補プール・430人サンプル）で機能していないことが判明した。
`question_pool`（250本）から回答済みを除いた候補は1ユーザーあたり200件超あり、この規模では
「平均-1σを下回る作品」がほぼ必ず複数見つかってしまい、事実上「常に上限5件が埋まる」という
件数固定と同じ挙動になっていた。指示に従い、**条件を絶対しきい値のみ**（`予測完走率 < しきい値`、
低い順に上限5件、該当0件なら空配列）に変更した。

### 0件率の実測とチューニング結果

| しきい値 | at_risk=0件のユーザー割合 |
|---|---|
| 0.90 | 0.00% |
| 0.85 | 0.00% |
| 0.80 | 0.00% |

**指示された調整（<20%なら0.80へ）を適用しても、0件率は0.00%のまま変わらなかった。**
目安とされていた4〜6割には遠く及ばない。原因は同じく候補プールの規模にある。
候補が200件超あると、よほど高いしきい値（99%近辺）でない限り、常に5件以上が
しきい値を下回ってしまう。**絶対しきい値も、この規模の候補プールでは実質的に
「上限5件固定」と同じ挙動になりやすい**という点は、相対条件のときと同種の課題として残っている。
これ以上のしきい値調整は指示の範囲外のため実施していない。0.80のまま据え置き、
`at_risk_threshold`（スカラー値）としてレスポンスに含めている。この点はご判断を仰ぎたい。

### 修正2-b: percentile を削除

「候補群の中での位置」という定義は、同じユーザー・同じ作品でも候補セットが変わるたびに
数値が変動するため指標として不適切、との指摘を反映し `percentile` を完全に削除した。
`relative_risk`（(1-個人完走率)/(1-母集団完走率)）のみを残しており、こちらは候補セットに
依存せず同じ入力に対して常に同じ値を返す。

### エッジケーステスト

`docs/ui_spec.md` 7章のエラー・エッジケース表に対応する3パターンを実データ（question_poolの
実在作品）で検証した。いずれもエラーにならず、妥当な値を返すことを確認した。

| ケース | `/predict` | `/predict/single` |
|---|---|---|
| 「途中で止まった」0件（全回答が好き/完走） | OK（endurance_episodes=153, completion_rate=1.0） | OK（confidence=medium, evidence 3件） |
| 「完走」0件（全回答が途中で止まった） | OK（endurance_episodes=0, completion_rate=0.0） | OK（同上） |
| 回答が最小本数（5本）ちょうど、3種混在 | OK | OK |

このテストの過程で、前回報告済みの「離脱回答が0件だと `cos_dropped` 列が全てNoneになり
LightGBMがエラーになる」バグの修正（`api/ml/inference.py`）が、逆側のケース
（完走回答が0件で `cos_completed` が全てNoneになる場合）にも正しく効くことを確認できた。

## 追記2: at_risk 候補プールを話題作（登録者数上位300）に限定

### 修正1-c

- `at_risk` の候補を `store.top300_by_registration`（登録者数上位300作品）のうち未回答のものに変更
- `will_complete` / `baseline_comparison` は従来より広い候補プール `store.top3000_by_registration`
  （登録者数上位3,000作品。question_pool選定・Phase 2の人気順比較分析と同じ候補ユニバース）に変更し、
  話題作に絞らないようにした
- `at_risk_threshold` を0.85に戻した

### 実測結果

- **評価ユーザー数**: 131人（キャッシュ済みテストユーザーから抽出）
- **at_risk=0件のユーザー割合: 0.00%**
- **返された作品の予測完走率の分布**（n=655件）: 最小4.9% / 5%点5.5% / 25%点6.3% / 中央値10.1% / 75%点14.2% / 95%点21.0% / 最大21.1%
- **返された作品の登録者数の分布**（n=655件）: 最小482,725 / 中央値707,976 / 最大1,352,724。**すべて登録者数48万人以上であり、話題作への限定は機能している**

0件率は目安（4〜6割）に届いておらず、依然として0%だった。ただし**理由は前回とは異なる**。
前回（候補200件超）は「候補が多いこと自体による統計的必然」が主因だったのに対し、今回
（候補300件・話題作限定）は、**話数の長さが原因で説明できる場合と、モデルの重大なバグに
起因する場合の両方が混在している**ことが判明した。

### 【重大な発見】特定の「まだ完結していない話題作」で anime_avg_completion_rate_A が0近辺になるバグ

at_riskに実際に返された作品を調べたところ、71人中ほぼ全員（一部100%）に同じ5作品
（ONE PIECE、BORUTO -NARUTO NEXT GENERATIONS-、ブラッククローバー、約束のネバーランド、
呪術廻戦）が出現しており、ユーザーごとの個人化ではなくデータ側の欠陥である疑いが強かった。
実際に確認したところ、これらの作品の `anime_avg_completion_rate_A`（モデルの主要特徴量、
重要度56.9%）が**軒並み0.0**だった（例: ONE PIECE 0.0, ブラッククローバー 0.0, 呪術廻戦 0.0。
n_labeledはそれぞれ580件・352件・22件と、データ不足ではない）。

原因は特定できた。`anime.csv` 側の集計（参考値、母集団は異なる）を見ると:

| 作品 | Aired | Completed | Dropped | Watching |
|---|---|---|---|---|
| One Piece | Oct 20, 1999 to **?**（放送中） | 33 | 136,245 | 887,333 |
| Black Clover (TV) | Oct 2017 - Mar 2021（本データセットのスナップショット時点で放送中） | 103 | 89,594 | 530,324 |
| Jujutsu Kaisen (TV) | Oct 2020 to **?**（放送開始直後） | 299 | 5,177 | 533,016 |
| 約束のネバーランド 2nd Season | Jan 2021 to **?**（放送中） | 60 | 6,966 | 260,775 |

**これらはすべてデータ収集時点で放送継続中（未完結）の作品である。** 放送中の作品は
定義上「完走（全話視聴済み）」になり得ないため、視聴を継続しているファンはほぼ全員
`watching`（除外対象）に滞留し、`completed`/`dropped` の2値に「決着」がついているのは
ほぼ「離脱した人」だけという構造的な偏り（右側打ち切り = right censoring）が生じている。
結果として、**放送中の作品はどれだけ人気・高評価であっても anime_avg_completion_rate が
機械的にほぼ0になり、モデルが「離脱率ほぼ100%」と誤って学習してしまう。**

これは登録者数上位300件（話題作）に候補を絞ったことで初めて顕在化した問題である。
話題作＝現在人気の高い作品には放送中のヒット作が多く含まれるため、この偏りの影響を
真正面から受けてしまう。**これは設計判断を要する不具合**であり（例: 放送中の作品を
anime_avg特徴量の対象外にしてカタログの `Completed/(Completed+Dropped)` 列で代替する、
放送中フラグを別特徴量として持たせる、候補選定時に放送中作品を除外する、等の対応が考えられる）、
今回のスコープでは修正していない。**Phase 4着手前にご判断をお願いしたい。**

## 追記3: 放送中作品（右側打ち切り）への対応

### 修正1: 放送中作品の判定

- `anime.csv` の `Aired` に終了日がない（`"... to ?"` パターン）作品: **525本**
- `watching_ratio`（=`Watching / (Watching+Completed+Dropped)`、`animelist.csv`全体から算出、denom≥50の作品14,056本が対象）の分布を、Aired基準で「放送中」/「完結」に分けて比較したところ、**完結作品の99パーセンタイルが0.334、放送中作品の5パーセンタイルが0.405**と明確な分離があった。安全マージンを見て**しきい値0.5**を採用
- **最終判定 = Aired基準（525本）OR watching_ratio>0.5（230本）の和集合 = 577本**
- `animelist.csv` 上のレコード数: 全ステータス合計1,813,293件（全体の1.660%）。学習データ相当（定義A: status 2,4）では107,624件（定義A全体の0.149%）

### 修正2: 特徴量を0.0からNaNへ

`anime_avg_completion_rate_A` を、放送中577作品については実績値ではなくNaNとして扱うよう
`api/services/data_store.py` の `anime_avg_for_model()` を変更した。

### 修正3: 学習データへの影響評価と判断

学習データ相当に占める割合は **0.149%（1%未満）** だったため、当初の判断基準に従えば
「推論時対応のみで可」となるはずだった。**しかし実際に検証したところ、推論時のみNaNに
差し替えても予測値が全く変化しないことが判明した**（ONE PIECEの離脱予測確率は
NaN指定でも0.0指定でも同一の0.9320）。理由はLightGBMの欠損値処理にある。学習時に
一度もこの特徴量がNaNだった行が存在しなかったため、モデルは「NaNをどちらに分岐させるか」
を学習しておらず、既存の0.0近辺の分岐方向へ暗黙的にルーティングしていた。

**この結果を受け、1%未満という基準に反して、モデルを再学習した。** 理由は「学習データへの
影響が小さいから再学習不要」という当初の基準が、「推論時にNaNを渡せばモデルが他の特徴量で
判断してくれる」という前提の上に成り立っていたが、その前提自体が誤りだったため。
訓練データ側でも放送中作品のanime_avgをNaN化して再学習した結果:

- テストAUC: 0.8226 → 0.8226（変化なし）、PR-AUC: 0.3024 → 0.3023（変化なし）。**全体性能への影響はなし**
- 訓練データに占める放送中作品の行の割合: 0.175%（従来の全体推計0.149%と整合）

### 【新たな発見】特徴量を直しても解決しない、より深い問題

再学習後もONE PIECE等の予測は変わらず低いままだった（例: ONE PIECE 離脱予測確率0.93）。
原因を調査したところ、**`anime_avg_completion_rate_A` という特徴量だけでなく、
学習に使う生ラベルそのものが右側打ち切りの影響を受けている**ことが判明した。
`animelist.csv` 全体でONE PIECE（anime_id=21）について「決着」している
（completed または dropped の）行を数えたところ、**19,100件中19,098件がdropped、
completedはわずか2件**だった。放送中の作品は構造上「完走」した人がほぼ存在し得ないため、
モデルが学習する肝心の正解ラベル自体が「ほぼ全員離脱」に偏っている。これは特徴量の
欠損値処理では原理的に解決できない問題であり、今回のスコープ（推論時対応 or 再学習の
二択）を超える、より根本的な制約である。

**対応として、`at_risk` と `will_complete` の候補プールから放送中作品577本を除外した。**
理由: 予測値そのものが集団レベルの構造的偏りであり個人化された判断材料になっていない
以上、これらの機能（「あなたには続かないかも」「知らない良作」）の趣旨に反する。
一方 `POST /predict/single` は特定作品を名指しで聞かれた場合に答える機能のため除外せず、
`is_ongoing: true` と `confidence: "low"` を返して不確実性を明示する設計のままとした。

### 修正4: レスポンスへの is_ongoing 追加

`AtRiskItem` / `WillCompleteItem`（`/predict`）、および `/predict/single` のレスポンスに
`is_ongoing` を追加した。`/predict/single` で `is_ongoing: true` の場合、`is_estimated` と
同様に `confidence` を強制的に `"low"` にする（`is_estimated`自体は独立したフィールドのまま。
原因が異なる＝カタログに存在しない場合とカタログはあるが打ち切りの場合、で文言を出し分ける）。

### 修正5: UI仕様書の更新

`docs/ui_spec.md` 5.6 の直後に「5.6b 放送継続中の作品の場合」を追加し、指定の文言
（「放送中の作品のため、完走データが不足しています。内容の傾向から推定しています」）を
含むモック画面を追加した。`is_estimated`と`is_ongoing`は原因が異なるため別フィールドとして
返るが、UI上の扱い（「推定」表示・信頼度「低」固定）は共通と明記した。

### 再測定結果

修正後、`/predict` を通じて131人（テストユーザーからサンプル）で実測。

| 指標 | 修正前（放送中作品を候補に含む） | 修正後（放送中作品を候補から除外） |
|---|---|---|
| at_risk=0件のユーザー割合 | 0.00% | **32.82%** |
| 予測完走率の分布 | 4.9%〜21.1%（中央値10.1%） | **32.5%〜84.7%（中央値71.5%）** |
| ユニークな出現作品数 | 6作品 | **9作品** |
| 最頻出作品の出現率 | ONE PIECE等が100%近辺 | ナルト- 疾風伝 67.2%（最多）〜ディー・グレイマン 2.3%（最少） |

**同じ5作品が全員に出るという症状は解消した。** 依然としてナルト-疾風伝（67.2%）・
BLEACH（49.6%）・FAIRY TAIL（47.3%）などの超長編シリーズが上位に残るが、これらは
放送が完結しており実績データも健全（右側打ち切りの影響がない）ため、「長編ゆえに多くの
ユーザーにとって完走が難しい」という**正当な個人化されたシグナル**である。0件率32.82%・
完走率分布32.5%〜84.7%という値も、初回に想定していた目安（4〜6割）に近い、妥当な水準に
収まった。

**Phase 4（フロントエンド）にはまだ着手していない。**
