# 修正レポート: will_complete（ブロック4「完走できる作品」）ロジックの修正

## 問題

`will_complete` は予測完走率（`completion_prob`）の降順でソートしていたため、1話の映画・OVA
（定義上ほぼ100%完走）が上位を独占し、推薦として意味をなしていなかった。「測れる指標を
最大化すると意味のない答えに収束する」という、本プロジェクトが繰り返し検証してきた構造
（`anime_avg_completion_rate`のみのモデルが人気順よりわずかにしか勝てない問題、
episode_gapの外れ値問題などと同種）が、この推薦ロジックにも存在していた。

## 修正内容（`api/services/predict.py`, `api/services/explain.py`）

### 修正1: 候補フィルタ

`_will_complete_candidate_pool()` で以下を候補から除外する。

- Type が Movie / Music / Special（`store.anime_type()`を新設）
- 総話数が6話以下
- 登録者数が50,000未満
- MALスコアが7.0未満（`store.score()`を新設）

### 修正2: ソート基準を相対完走率に変更

```
relative_completion = 予測完走率 / その作品の母集団完走率
```

`_relative_completion()`を新設。at_riskの`relative_risk = (1-個人完走率)/(1-母集団完走率)`と
対称の設計（母集団完走率が0に近い作品は分母を0.01に床上げする点も同様）。
レスポンス（`WillCompleteItem`）に `relative_completion` と `population_completion_rate` を
追加した。

### 修正3: 話数バケットとの連動

`_will_complete_candidate_pool()` で、候補をユーザーの「合う話数」バケット
（`best_episode_bucket`）、またはその1つ上のバケットに属する作品に限定する。
該当作品がWILL_COMPLETE_MIN_POOL_SIZE(10)件に満たない場合のみ、隣接バケット
（1つ下・2つ上）まで広げる。`best_episode_bucket`がNone（データ不足で「合う話数」が
決まらない場合）はバケット制限をかけない。

### 修正4: 多様性の確保

`_select_diverse_will_complete()` で、`relative_completion`降順のリストを先頭から走査し、
主ジャンル（`genres[0]`）ごとの選出数が3件に達したらスキップする貪欲法で上位10件を選ぶ。

### 修正5: 表示の変更

- `docs/ui_spec.md` 4.6を更新。予測完走率と母集団完走率を両方表示するモックアップに変更し、
  候補選定ロジック（修正1〜4）を仕様として明文化した
- `explain.build_will_complete_reason()`に`completion_prob`・`population_completion_rate`を
  渡すよう変更し、母集団完走率が低く（60%未満）かつ予測完走率との差が大きい（15pt超）場合は
  「一般には完走されにくいですが、あなたの傾向なら見切れそうです」という差分説明の文言を返す
  ようにした。それ以外は従来どおりジャンル・埋め込み類似度による理由を使う
- `frontend/src/components/WillCompleteBlock.tsx`を更新し、「完走率89%（一般70%）」のように
  両方の数値を表示するようにした（型定義`frontend/src/api/types.ts`も追従済み）

### 確認結果

- **1話・映画作品**: 3人×10件＝30件中、**0件**（最短話数はユーザー1の巌窟王・ユーザー2の
  生徒会役員共 8話。すべてWILL_COMPLETE_MIN_EPISODES=6話超）
- **話数バケットとの連動**: 各ユーザーの「合う話数」バケットの範囲に一致している。
  ユーザー1（合う話数=14〜26話）は話数22〜50話（14〜26話バケット＋1つ上の27〜50話バケット）
  に収まっている。ユーザー2・3（合う話数=〜13話）は話数8〜26話（〜13話バケット＋1つ上の
  14〜26話バケット）に収まっている。バケット制限外（例: 51話〜や、〜13話バケットのみが
  「合う話数」のユーザーで50話台の長編）は出現しなかった
- **母集団完走率より予測完走率が高いか**: 3人×10件＝30件**すべて**で
  `completion_prob > population_completion_rate`（`relative_completion`が全件1.00〜1.11で
  1.0以上）。これは「一般的にも完走されやすい作品の中で、特にユーザー本人の傾向で
  さらに完走しやすい作品」を優先的に選んでいることを意味し、修正2の意図どおりに機能している

参考: 修正直後に別シードで10人分を確認した際も同様の結果（30件→100件でも1話作品は0件、
`best_episode_bucket`が「データ不足」のユーザーではバケット制限が正しく解除され長編候補
（銀河英雄伝説110話・あしたのジョー79話等）が出現することも確認済み）。

## 実装環境上の制約（今回スキップした確認）

このマシンはiCloud Drive「Macのストレージを最適化」の影響でプロジェクトファイルが
評価対象外の状態（dataless placeholder）になっており、`tsc`/`vite build`など
`node_modules`を広く走査する操作が読み込み待ちで長時間停止する問題が悪化していた。
ユーザーの指示により、今回は型チェック・フロントエンドビルドを実施していない。
`frontend/src/api/types.ts`・`frontend/src/components/WillCompleteBlock.tsx`への変更は
目視レビュー済みだが、TypeScriptコンパイラによる型検証は未実施である点に留意されたい。
バックエンドの動作確認は、既に起動済みのプロセスに対する実HTTPリクエストで行っており、
この問題の影響を受けていない。
