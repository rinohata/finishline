# 修正レポート: 耐久話数の指標変更・脱落曲線グラフ・平均値ラベル整理

Phase 4 P0 完了後にユーザーから指摘された5件の修正。実際にバックエンド（FastAPI）・
フロントエンド（vite preview 静的ビルド）を起動し、Playwright制御下の実ブラウザで
動作確認した（モックデータは使用していない）。

## 修正1: 耐久話数 →「話数レンジ別完走率」

### 問題
`compute_endurance_episodes`（完走率が50%を切る話数）は、長編を1本でも完走した
ユーザーでは50%を切らず、その作品の話数（例: 358話）がそのまま返っていた。
外れ値1本で指標全体が壊れ、「完走できる話数 358話」という意味をなさない表示になっていた。

### 対応
`api/services/profile.py` に以下を追加した。

- `EPISODE_BUCKET_DEFS`: 4バケット定義（〜13話 / 14〜26話 / 27〜50話 / 51話〜）
- `compute_episode_buckets(responses)`: バケットごとの完走率・本数を算出。
  本数0件は `completion_rate: null` にする
- `best_episode_bucket(buckets)`: 本数3本以上のバケットのうち完走率最高のものを返す。
  該当なしなら `None`（＝「データ不足」）

`ProfileOut` レスポンスに `episode_buckets`（4件固定の配列）と `best_episode_bucket`
を追加した。`generate_type_name` もこの「合う話数」バケットを使うよう変更し、タイプ名
生成が外れ値に引きずられなくなった。

フロントエンド（`TypeDiagnosisCard.tsx`）は「完走できる話数」の生数字表示を廃止し、
「合う話数」＝バケットのレンジ文字列（例: 「14〜26話」）または「データ不足」を表示。
下部にバケット4件の完走率テーブルを追加した。

### 実機確認
実データで6本回答（うち5本が51話以上）した結果、`endurance_episodes`（旧指標）は
`0`（=完走が一度も過半数を維持できず全滅扱い）だったが、新指標では
「51話〜」バケットが本数5件・完走率80%で正しく「合う話数」に選ばれ、タイプ名も
「長距離・熱血・王道派タイプ」と実態を反映した。

## 修正2: 特徴量への影響確認

`episode_gap`（候補作品の話数 − ユーザーの耐久話数）は引き続き旧定義の
`compute_endurance_episodes` を使っている（学習時の特徴量定義と揃えるため、
今回は変更していない）。この関数がモデル特徴量としてもどれだけ外れ値に弱いかを
実データで検証した。

**検証方法**: `notebooks/02_model.ipynb` と同一の手順（SEED=42, 15,000ユーザーを
user_id単位で70/15/15分割）でテストユーザー2,250人を再現し、N=20入力制限
シミュレーション下で `compute_endurance_episodes` の分布を集計した
（スクリプト: セッション内の一時ファイルで実行、再現可能）。

| 統計量 | 値 |
|---|---|
| 集計対象 | 2,158人 |
| 中央値 | 175話 |
| 75%点 | 220話 |
| 95%点 | 366話 |
| 99%点 | 1,787話 |
| 最大値 | 1,787話 |
| **100話超の割合** | **54.31%（1,172/2,158人）** |

**結論**: 100話超が3割どころか過半数（54.3%）に達しており、`episode_gap` は
テストユーザーの半数以上で「数百話」を基準にした差分になっている。これは
話数ギャップが実質的にほぼ常に大きな負の値（候補作品話数 ≪ ユーザーの見かけ上の
耐久話数）になり、特徴量として意味のある分散を持てていない可能性が高いことを示す。

**提案**: `episode_gap` を「バケットインデックスの差」（新設した
`bucket_index_for_episodes(候補話数) - best_episode_bucketのindex`、0〜3の整数）
に置き換えることを提案する。ただしこれは学習用特徴量の定義変更であり、モデルの
再学習・AUC/PR-AUCへの影響評価（Phase 2の評価表と同じ形式での再検証）が必要になる。
**今回の修正では実施していない。** 再学習を伴うため、着手前にユーザーの判断を仰ぐこと。

## 修正3: 脱落曲線グラフ（ブロック5）をバケット表示に変更

`api/services/predict.py` の `_build_curve` を、実測話数ではなく
`EPISODE_BUCKET_DEFS` の4バケット上限を固定目盛りとして使うよう変更した
（各目盛りまでの累積完走率という意味は維持し、X軸の刻み方だけを変えた）。
回答が届いていないバケットは点を打たない。

`CurvePoint` のフィールドを `episodes: number` → `range: string` に変更し、
`DropoutCurveChart.tsx` のX座標計算を実測話数の比例配置から配列インデックスの
等間隔配置に変更した。

実機確認: 6本回答（14〜26話, 27〜50話, 51話〜 の3バケットに分布）で、
X軸ラベルが「14〜26話 / 27〜50話 / 51話〜」と重なりなく表示されることを確認した。

## 修正4: 平均値ラベルの整理

2つの「平均」の算出元を確認した結果、**どちらも定義B（完走率算出は一貫して定義B、
Phase 2の定義A/Bピボットの影響を受けていない）だが、算出母集団が異なる別の指標**
であることを確認した（A/B定義の混在は無かった）。

| 表示箇所 | 旧ラベル | 算出元 | 内容 |
|---|---|---|---|
| ブロック2（診断カード） | 「平均」 | `store.pool_completion_rate_mean` | 質問プール(約250作品)全体の完走率の単純平均 |
| ブロック1/D・ブロック3（単体判定・at_risk） | 「一般平均」 | `store.population_completion_rate(anime_id)` | **その候補作品1本**の母集団完走率 |

同じものではなく別の指標のため、統一ではなくラベルで区別する対応を取った。
ブロック2側を「**全作品平均**」に変更し、「一般平均」（作品固有の値）と混同しないようにした。
バックエンドのコード側にも算出元の違いを明記するコメントを追加した。

## 修正5: 脱落曲線グラフの1話表示

`notebooks/01_aggregation.ipynb` の設計どおり、`peak_dropout_episode` は
1話を除いたハザード率最大の話数として既に正しく算出されていた（1話は「様子見離脱」で
常に高くなるため意図的に除外）。ただし `dropout_curve` 配列自体には1話のデータが
そのまま含まれており、`SingleAnimeDropoutCurve.tsx` がバー描画時に1話とpeakを
区別せず塗っていたため、1話が最も高い棒として表示されつつ隣の話数が赤（peak）になる
という矛盾が起きていた。バックエンドのデータ・ロジックは変更せず、フロントエンドの
表示のみを修正:

- 1話のバーをグレー（`#c9ced6`）に固定し、peak色・通常色と視覚的に区別
- グラフ下に「※ 1話（様子見離脱のため除外）はグレーで表示しています」の注記を追加

実機確認（デスノート）: 1話がグレー、25話（peak）が赤で正しく描画されることを確認した。
