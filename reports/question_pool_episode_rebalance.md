# question_pool の話数構成是正

## 問題

話数バケット（〜13話/14〜26話/27〜50話/51話〜）ごとの完走率を理由文・特徴量に
使う際、ユーザーの回答20本のうち各バケットに割り振られる本数が少なすぎ、
「27〜50話」「51話〜」のバケットが恒常的にデータ不足（`MIN_BUCKET_COUNT=3`未満）
になっていた。

原因は`data/question_pool.json`（250本）の話数構成が短編に著しく偏っていたこと。

| バケット | 旧question_pool |
|---|---|
| 〜13話 | 50.0%（125本） |
| 14〜26話 | 34.0%（85本） |
| 27〜50話 | 3.6%（9本） |
| 51話〜 | 12.4%（31本） |

旧選定ロジック（`notebooks/01_aggregation.ipynb`）は、完走率0.5に近いほど高スコアに
なるエントロピー指標（split_score）優先の貪欲法に、話数レンジの**上限**キャップ
（`episode_cap`）しか持たせておらず、**下限**の保証が無かった。完走率0.5付近を
優先すると、母集団完走率が相対的に低い長編（101話〜で89%、〜13話で96%）ほど
split_score上位に来にくく、機械的に短編へ偏る結果になっていた。

## 話数分布・母集団完走率の調査

`anime.csv`の総話数分布（総話数既知17,046作品）:

| 区間 | 作品数 | 母集団完走率(定義A、anime.csv公式Completed/Dropped集計) |
|---|---|---|
| 1〜13話 | 14,146 | 95.6% |
| 14〜26話 | 1,438 | 94.3% |
| 27〜50話 | 681 | 93.5% |
| 51〜100話 | 584 | 92.4% |
| 101〜200話 | 143 | 89.2% |
| 201話〜 | 54 | 89.0% |

話数が増えるほど完走率は単調に下がるが、変化は緩やか。もっとも差が大きいのは
51〜100話と101話〜の間（3.3pt差、p値は視聴者数が数百万件のため参考にならず、
実質差＝pt差で判断すべき）。101〜200話と201話〜の間はほぼ差が無い（0.2pt）ため、
「51話〜」をさらに細分化する根拠は現状薄い。この分析結果を受け、バケット分割
自体は保留し、先に質問プールの話数構成是正を優先することにした。

## 修正: scripts/build_question_pool.py

話数4レンジ（〜13/14〜26/27〜50/51話〜）それぞれに最低本数（60/60/50/50、
候補数が少ないレンジ＝希少なレンジから先に確保）を保証したうえで、残り30本を
split_score降順の自由選定とする二段階ロジックに変更した。制約は維持:

- 登録者数（`anime.csv` Members列）上位3,000件から選定
- Type が Movie/Music/**Special**/Unknown は除外（Specialを新たに追加）
- 登録者数上位200位以内から50本を無条件確保（認知度の担保）
- ジャンル・年代の分散化（`genre_cap`/`year_cap`は上限内選定で優先し、
  埋まりきらない場合のみ上限を外した補充パスで必ず最低本数を満たす）

`completion_rate`（母集団完走率・定義B）は`scripts/build_lookups.py`が生成する
`data/processed/anime_population_completion_rate_B.json`をそのまま使用した。

実行結果、全レンジとも上限内選定だけで最低本数を満たせ、補充パス（上限を外した
強制追加）は一度も発動しなかった。

## 検証結果

### 1. 新question_poolの話数構成比

| バケット | 旧 | 新 |
|---|---|---|
| 〜13話 | 50.0%（125本） | 36.0%（90本） |
| 14〜26話 | 34.0%（85本） | 24.0%（60本） |
| 27〜50話 | 3.6%（9本） | 20.0%（50本） |
| 51話〜 | 12.4%（31本） | 20.0%（50本） |

旧poolとの共通は139本（55.6%）、入れ替わりは111本（44.4%）。

### 2. テストユーザー20人シミュレーション（データ不足率、3本未満）

| バケット | 旧 | 新 |
|---|---|---|
| 〜13話 | 10% | 15% |
| 14〜26話 | 0% | 0% |
| 27〜50話 | 100% | 90% |
| 51話〜 | 60% | 50% |

改善はしたが「期待値4本以上」には届かなかった。原因は、母集団側でも
27〜50話に該当する上位3,000件中の候補が109件（101〜200話は143作品、
201話〜は54作品）しかなく、プール構成を変えても実際にその話数帯を
視聴しているユーザー自体が少ないため、プール改善だけでは分母の希少性を
解消しきれないこと。

### 3. 認知度の確認（訂正あり）

当初`split_score`単独ソートで「先頭20本中0/20本が登録者数上位200位以内」と
誤って報告した。実際のアプリの「おすすめ」デフォルト表示は`api/services/search.py`
の複合スコア（`split_score×25% + popularity_percentile×75%`、
`POPULARITY_WEIGHT=0.75`、旧poolに対して「先頭20本中4本以上」を満たすよう
チューニング済みの定数）でソートされていることに後から気づき、再計算した。

**複合スコアで正しく計算した結果: 先頭20本中、登録者数上位200位以内は
旧4本／新4本で変化なし。** `POPULARITY_WEIGHT`の再チューニングは不要と確認できた。

### 4. 完走率分布・情報量とのトレードオフ

| | 旧 | 新 |
|---|---|---|
| completion_rate 中央値 | 0.7232 | 0.6977 |
| completion_rate 0.85以上（低情報量） | 45件 | 55件（+10） |
| split_score 中央値 | 0.8511 | 0.8827 |

0.85以上の増加はほぼ「27〜50話」バケット単独（2件→13件）が原因。このバケットは
候補が109件しかない中で50件（46%）を確保する必要があり、split_score上位だけでは
埋まらず完走率の高い（＝情報量の低い）作品も混ざった。「51話〜」は候補152件から
50件（33%）で済んだため、split_score中央値0.895→0.893・0.85以上2件→3件と
情報量への影響はごく軽微だった。

## 影響範囲: モデル再学習の要否

再学習を推奨する（本レポート作成時点では未実施）。

`scripts/train_model.py`の`build_target_rows`は`data/question_pool.json`の
`pool_ids`を使って、学習時に「ユーザーの回答として何を入力とみなすか」
「何を予測ターゲットとして使うか」を決めている。プールが44.4%入れ替わったことで、
学習時にシミュレートされる回答パターンの話数構成が、本番でユーザーが実際に
目にする質問プールの構成とズレる。`predict.py`は推論時に`pool_ids`を参照しない
ため、再学習しなくても即座にAPIが壊れることはないが、学習時分布と本番分布の
ズレによる精度・キャリブレーションの緩やかな劣化リスクがある。
